# Security and privacy
Implemented: OTP login (hashed codes, 5 min expiry, 5 attempts, single use); role-based admin (super, state, district, department, verification officer, public viewer) with state/city scope; admin complaint lists carry no citizen identity; consent recorded in audit log (submit, share personal data, representative); rate limit (120 req/min per token/IP, configurable); upload checks (JPEG/PNG magic bytes, 5 MB cap, hashed filename); public feed hides identity, rounds coordinates to ~100 m, shows photos only after a verification officer approves; account deletion anonymises; audit log for sensitive actions; credentials only from environment variables; SQL parameterised; HTML output escaped; nosniff header.
NOT implemented (honest): encryption at rest and TLS (use a host/disk that provides them), SMS delivery of OTP, malware scanning, EXIF validation, automatic face/number-plate blurring (photos stay private until manually approved), password login, CAPTCHA for public endpoints, data retention scheduler, DPDP legal review, backups automation.
Never done: bypassing government CAPTCHA/OTP, impersonating a citizen, fake acknowledgements.

## Seva Setu document vault (Phase 4-5)
Implemented: private citizen document vault (JPEG/PNG/PDF, magic-byte checked, 5 MB cap, sha256 recorded); document bytes served only through an authenticated endpoint with per-request ownership check (other citizens get 404); the public /uploads route refuses document keys; operator document access requires an active, per-application citizen consent (operator_document_access) and is logged with the consent id; consent can be revoked by the citizen at any time, which immediately blocks further operator views; every upload/view/delete is in document_access_logs; deletes are soft (row kept for audit).
NOT implemented (honest): encryption at rest for document bytes, malware scanning (see plan below), EXIF stripping, download of documents by operators is blocked only by UI convention (bytes open inline), operator onboarding/verification workflow (operators are admin-created tokens today).

## Malware scanning - current limit and plan
Current limit: no malware scan runs on uploaded photos or vault documents. Mitigations already in place: only real JPEG/PNG/PDF accepted (magic bytes, not extension), 5 MB cap, files stored under random hashed names, never executed, images/PDFs served inline with nosniff from a private endpoint, public uploads route never exposes vault documents. Residual risk: a malicious PDF/image crafted to exploit a viewer bug could reach an operator's or citizen's browser.
Plan (free tools only):
1. Add a scan worker: ClamAV (open source) running as a separate Render background worker (Docker) or a cron job on the same host; new uploads are stored with scan_status='pending' and are not viewable by operators until scan_status='clean'.
2. Flow: upload -> quarantine prefix -> ClamAV scan (clamd over TCP or clamscan CLI) -> clean: move to live prefix + mark clean; infected: delete object, mark rejected, notify citizen, audit.
3. Citizen files remain visible to the owner while pending (their own risk, clearly labelled "scan pending"); operator view requires scan clean AND active consent.
4. Fallback if ClamAV cannot run on the free tier: hash-reputation check (sha256 against the free MalwareBazaar API by abuse.ch) plus strict content-type sniffing, with the limit disclosed to operators in the console.
